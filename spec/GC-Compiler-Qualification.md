# GC-Compiler-Qualification — Qualification of Compilation Capabilities

**Status:** Normative framework, v0.1.0

## 1. Qualification object

A governance compiler may be a human process, software tool, AI-assisted workflow, organizational capability, or hybrid system. A qualification claim MUST identify the actual capability being relied upon, not merely a product name.

Qualification is an intended-use claim. It MUST identify the input class, output/target profile, consequence/assurance context, supported semantics, dependencies, environment assumptions, and limitations for which the capability is qualified.

## 2. Qualification is not package validation

A qualified compiler can produce a defective package; an unqualified compiler can produce a package that happens to validate. Therefore:

```text
CompilerQualified(T, U) does not imply PackageValid(P)
PackageValid(P) does not imply CompilerQualified(T, U)
```

A conformance claim MUST keep these objects separate.

## 3. Minimum qualification dimensions

A qualification profile SHOULD evaluate, proportionate to intended use:

1. authorized-source handling and source identity preservation;
2. domain/interpretive competence where interpretation is within the capability boundary;
3. semantic fidelity across transformations;
4. repeatability/reproducibility under a declared environment profile;
5. traceability generation/preservation;
6. diagnostic behavior, including refusal/indeterminate results;
7. conflict, coverage, and completeness-analysis capability claimed;
8. test coverage and negative/fault testing;
9. provenance generation/preservation;
10. security/access control around authoritative transformations;
11. dependency/version/configuration control;
12. target projection behavior;
13. change-impact and requalification rules; and
14. independent review where required by the assurance profile.

## 4. AI-assisted compilation

When AI assists interpretation, mapping, transformation, testing, or artifact generation, the qualification claim MUST identify the role delegated to the AI-assisted component and the control by which its output becomes authoritative.

AI-generated interpretation or code MUST NOT be treated as authoritative solely because it was generated by a capable model. Material semantic decisions remain subject to the authority and review requirements of the applicable profile.

Where a probabilistic component cannot reproduce byte-identical output, the qualification profile MUST define the reproducibility/equivalence criterion actually required (for example structural, semantic, or decision equivalence over a declared domain).

## 5. Qualification evidence package

A qualification evidence package SHOULD identify:

- capability/tool identity and version;
- intended-use profile;
- supported GIR/spec/profile versions;
- qualified target projections;
- dependency/configuration baseline;
- test suites and coverage basis;
- known defects/limitations;
- semantic differential results;
- negative/fault tests;
- security review;
- independent review where applicable;
- qualification status and decision authority; and
- requalification triggers.

## 6. Requalification

Changes to semantics, compiler logic, AI model/provider/configuration, dependencies, canonicalization, target adapter, build environment, or security-relevant configuration MUST be assessed for qualification impact. A material change invalidates the affected qualification claim until re-established.
